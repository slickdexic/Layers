## The rule is settled; these are implementation checks

Equal layer-set names on different files or owning wiki pages are ordinary, valid identities. They are not a conflict or an architect decision. For example:

| Owning wiki page ID | File | Layer-set name | Meaning |
| --- | --- | --- | --- |
| 150 | `File:A.jpg` | `ABC` | One layer set |
| 150 | `File:B.jpg` | `ABC` | A different layer set |
| 151 | `File:A.jpg` | `ABC` | Another independent layer set |

These columns describe internal lookup context; the author writes only the file and `layerset=ABC`. Slides follow brief section 9: the owning wiki page and slide name identify the standalone slide. File and slide lookups must respect the content kind. PDF page numbers select internal parts of one document-wide layer set.

The reason to test equal labels is a confirmed implementation defect: `PageOwnedBinding::resolveNamed()` currently requires exactly one matching label across the owner's surfaces **before checking the file or kind**. `DrawingName::assertPublishable()` likewise counts labels across the page. Both still implement the superseded page-wide name rule. Tests must prove that full identities are used instead. The former heading "Two files and a slide share ABC" described regression fixtures poorly; it did not identify a product problem.

## What is already approved

The owner approved the following behaviour on September 30; this draft does not reopen it:

- Two files on the same owning page can each have a layer set called `ABC`. Repeated embeds of the same file and name on that page select one layer set.
- A PDF layer set covers the document. Its page surfaces share the layer set name, and the embed's `page=N` selects the page. Pages do not acquire user-facing ` (page N)` names.
- Slides are identified by their owning page and name. An image and a slide can have the same name.
- Authors write names without page IDs. Existing explicit owner IDs remain accepted input; another page's explicit ID never grants display or edit authority here.
- After migration, `layerset=on` means `Default`. Before completion, migration must preserve what a legacy show intent displayed, rewriting to the actual set name when needed. Hide intent behaviour remains unchanged.
- Rename updates the owning page's embeds in the same revision. Migration preserves names except real collisions and the approved multi-set slide case.

The handoff's file-scope exclusions and legacy migration treatment still need to be reconciled. That is not an unresolved naming model. The existing show aliases `true`, `all`, and `1` follow the J112 packet's stated rule, without changing the pre-migration boundary.

## Implementing a rename of one PDF layer set

The user renames the layer set once. All its PDF pages retain that same name. The following are server consistency checks against the current per-page storage representation, not independently nameable PDF pages or choices for the owner to make.

1. Compare retained surface IDs against the exact base. A PDF group is the old canonical file plus old normalized name, within that owning page. A changed name on one retained member expresses a rename of the whole retained group; unchanged members are included. Deleted members stay deleted.
2. One distinct requested new label renames all retained members and all direct embeds of that file/name, across PDF pages. Recompute the complete content and changed IDs before validation and authorization of changed sources. Renaming does not alter layers, coordinates, source version or surface IDs.
3. An internally inconsistent payload assigning different new names to page records of the same set is invalid. Refuse it without writing; do not pick a name by array order. The normal editor offers one layer-set name.
4. A case-only rename also applies one display spelling to the whole set. Conflicting display spellings inside a single rename payload remain invalid; existing normalized-name comparisons still determine identity.
5. Validate the final complete layer-set identities. `ABC` and `XYZ` on the same file and owning wiki page are distinct document-wide sets, even if their annotated pages do not overlap. A rename cannot silently merge them. An equal name on another file or owning wiki page is irrelevant to this check.
6. Evaluate scoped rename maps from the base, without cascading them through rewritten labels. Existing slide swap behaviour has a test and remains protected; do not accidentally outlaw or cascade a legitimate `A ↔ B` rename transaction. Any proposed restriction on swaps needs a separate decision.

Adding layers on a previously unannotated PDF page within the selected layer set retains that set's identity and name, including when the set is renamed in the same edit. The lead must make the internal publication operation express that membership consistently; the storage representation does not create a new product decision.

## Migration and legacy caller adaptation

The allocator needs the complete destination identity and the operation being performed. Adding PDF page 3's layers to an existing `ABC` must retain `ABC`; numbering it because page 1 is already stored would violate the approved model. Cases below describe legacy migration/copy implementation, not a choice between one layer set and separately named PDF pages.

| Situation | Required behavior or remaining migration work |
| --- | --- |
| File A has `ABC`; an independent layer set is added to file B as `ABC` | Keep `ABC`. This follows the approved file identity; file A's label does not reserve it. |
| Migration imports legacy PDF `ABC` pages 1 and 3, with no existing target identity | Allocate `ABC` once for the incoming group and retain that name on both surfaces, irrespective of processing order. This follows the approved PDF model. |
| A resumed migration already created page 1 `ABC`; its own page 3 is still pending | Reuse the recorded allocation for that same migration source group, including an earlier chosen suffix. Existing deterministic migration surface IDs are evidence of a prior copy. Do not infer continuity from name alone or change an already allocated group's name on resume. |
| Target has an unrelated `ABC` on PDF page 1; incoming legacy group has pages 1 and 3 | Page 1 collides. Choose a free group name once, e.g. `ABC 2`, for **both** incoming pages; do not produce page 1 `ABC 2` and page 3 `ABC`. Preserve the unrelated target content. This is a proposed allocation rule, not a recorded approval. |
| The destination layer set `ABC` already has layers on PDF page 1; an operation adds layers to page 3 of that same set | Keep the destination identity and name `ABC`. This is not a new layer set and never triggers name allocation. A request to copy a whole set into a separate set is a different operation; adapt the legacy caller to make the intended operation explicit. |
| Target already has `ABC 2` only on page 7; a new independent copy of `ABC` needs a suffix | A surface-only allocator could reuse `ABC 2` on page 3 and accidentally join it. For a new branch, reserve names at the whole-file group level and choose `ABC 3`. Joining an explicitly selected group uses page-level collision checks instead. |
| Incoming page 3 and the target group page 1 refer to different PDF timestamps/SHA values | Identity alone does not resolve the intended document version. Do not update either pin or treat hashes as independent layer-set identities. Confirm whether joining is refused or requires the later explicit file-update flow. The unapproved [J111 viewer proposal](J111_VIEWER_READ_PROPOSAL.md) recommends one pin for a newly assembled group and no automatic repair of existing mixed-version content; both packets need the same architect decision. |

For a duplicate page in a chosen destination group, reject or allocate a new group according to the approved operation; never overwrite that page's layers. Existing Import Append/Replace approval does not silently authorize those operations in a migration or the old copy endpoint.
